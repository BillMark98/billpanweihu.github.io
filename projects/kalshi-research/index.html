The thesis, stated narrowly

The goal is not to predict events. It is to estimate a fair probability, compare it to the market probability, and trade only where

edge = fair_probability − market_probability  >  fees + execution costs

Everything in the repository exists to make the right-hand side of that inequality trustworthy. If the market probability you computed is wrong, the edge is noise with a confident sign.

Four behaviours that break naive implementations

Each of these was verified against the live API rather than assumed. What they have in common is that they fail silently: the code runs, and the numbers still look like prices.

1. The order book has no asks

Kalshi returns two bid ladders — resting YES bids and resting NO bids. There is no ask side, because on a binary market it would be redundant. A contract pays $1.00 in total, so

buying NO at $0.60  ==  selling YES at $0.40

The YES ask ladder is the NO bid ladder reflected through the $1.00 payoff — and the reflection flips the ordering. The highest NO bid is the lowest YES ask:

yes_ask = 1.00 − no_bid

Read no_dollars as an ask ladder and every spread, mid and imbalance downstream is wrong. Observed live on a real market: the naive reading gave a $0.04 spread where the truth was $0.42.

That is the worst possible direction to be wrong in. It makes illiquid junk look like a tight, tradeable market — precisely the error that gets capital committed.

The independent check: the two sides of one tennis match quoted mids of 0.525 and 0.450, summing to 0.975 ≈ 1.00. Complementary binaries must sum to one, less the spread. The normaliser applies the reflection exactly once, and the complementary-sum test is what proves it.

2. Prices are fixed-point strings, not integer cents

yes_bid_dollars: "0.1200" carries four decimal places; volume_fp: "100.00" carries two, because fractional contracts are real. Tick structures can be sub-penny, so nothing may assume a one-cent grid. Everything stays in Decimal — a single float would quietly corrupt the warehouse, and the corruption would be invisible until it mattered.

3. Auto-generated combos dominate the default listing

KXMVE* multivariate event contracts are parlay-style combinations. They number in the thousands, are nearly all empty, and dominate the default market ordering — the first smoke run returned five markets with entirely empty books for this reason alone. The client defaults to excluding them.

4. Live endpoints reach back only about three months

Older data sits behind a separate historical surface whose cutoff moves over time, so backfill has to poll for the current cutoff and route accordingly. Not yet implemented, and listed as such.

Plus a fifth, on rate limits: a breach returns 429 with no Retry-After and no X-RateLimit-* headers, so the client has to schedule its own backoff rather than read one.

Read-only on purpose

KalshiClient exposes no write endpoints whatsoever. Not disabled, not flagged off — absent. That is what makes it safe to point at production, which in turn is what makes the verification above meaningful; testing microstructure assumptions against a demo venue would prove very little.

Honest status

The README carries a milestone scorecard that marks retry logic and rate limiting as "written, never executed", and lists the WebSocket feed, the PostgreSQL schema and incremental updates as not started.

One verification detail worth repeating: RSA request signing was confirmed with both a real key (200 on the balance endpoint) and a deliberately bogus one (401). The negative control is what makes the positive result mean anything — public endpoints ignore authentication entirely, so a completely broken signature would have "passed" against them.
