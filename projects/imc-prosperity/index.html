What this is

IMC Prosperity is a multi-round algorithmic trading competition. Each round introduces new instruments with different dynamics, you submit a Trader class, and it runs against a simulated exchange with position limits and other participants' bots.

I entered rounds one through five. The repository is less interesting as a finished strategy than as a record of how the strategy got there: twelve numbered versions of the round-five trader, seven named variants testing distinct hypotheses, and a set of postmortem notebooks written after the losses.

The local backtester came first

The competition gives you a submission endpoint and a score. That feedback loop is far too slow and far too coarse to develop against — you learn one number per submission, with no attribution.

So the first thing built was backtester.py, a local simulator that replays the provided order-book snapshots and executes a Trader against them. Everything after that was developed offline and submitted only once it beat the incumbent locally.

This is the single highest-leverage decision in the repository. It converts "did this help?" from a once-per-round question into a once-per-minute one.

Structure of a strategy

Every version decomposes the same three ways:

Alpha — what is fair value? For a stable instrument, a constant anchor confirmed by the distribution of the mid. For a volatile one, a signal: order-book imbalance, spread position, or a volume-weighted fair.

Execution — where do the orders go? Take liquidity when the book crosses fair by more than a threshold; otherwise quote around fair and wait.

Risk — how much inventory is tolerable, and how does quoting skew as the position fills?

Keeping these separate is what makes A/B testing meaningful. The variants/ directory tests exactly one of them at a time:

VariantHypothesis under test
trader_v7b_static_provenThe incumbent — control arm
trader_v7a_safe_adaptiveAdaptive fair value beats a static anchor
trader_v7c_spread_fadeFade wide spreads rather than quoting through them
trader_v7d_obi_alphaOrder-book imbalance predicts the next mid move
trader_v7e_vwap_fairVWAP is a better fair value than mid
trader_aggressive_vfLarger size on high-confidence signals
trader_no_hgAblation: remove the hedging leg entirely

Each is a full trader, not a flag, so they can be run head-to-head in the backtester without a combinatorial config space.

The exploratory work

Each round starts with an EDA pass before any strategy code, asking a fixed set of questions of the new instruments:

  • Distribution and time series of the mid — is fair value stationary?
  • Distribution of the top-of-book spread and depth — how often does free edge exist?
  • Return autocorrelation at lags 1–20 — momentum or mean reversion?
  • Order-book imbalance against the next-tick mid move — does it predict?
  • A periodogram on the mid — the rounds sometimes embed a periodic signal
  • Do trades cluster on one side and lead mid moves?

There is a decision gate at the end of the EDA: confirm or revise the fair-value assumption, and pick one signal to build on. Picking one is the discipline — with five instruments and twenty candidate signals, everything correlates with something.

The postmortems

analysis/ contains notebooks named after the P&L figures that prompted them — postmortem_544550, postmortem_549334, deep_diagnosis, comparison_v7v8v9. These reconstruct, from the execution logs, which specific decisions cost money.

They are the most useful artifacts in the repository. A version number tells you an ordering; a postmortem tells you why the ordering went that way. Several of the later strategy changes are directly traceable to a specific chart in one of these notebooks.

Before publishing: the wiki/ directory holds verbatim competition text from IMC and should be paraphrased or dropped, and temp.html plus the conversation_*.md files are working scratch rather than part of the project.
